# `feu.compat`

Registry-based package/Python-version compatibility resolution: given a
package name and a target environment, find out which versions of that
package are known to work.

## Concepts

- **`Target`** identifies the environment a constraint applies to:
  `python_version` and `free_threaded` (always concrete), plus optional
  `os`/`arch`. `None` on `os`/`arch` means "any" when stored in the
  registry, and "unspecified" when used as a lookup key.
- **`VersionRange`** is one contiguous `(min, max)` span of valid package
  versions; either bound may be `None` for unbounded. A package/target can
  have several disjoint ranges (e.g. a package supported `1.0`-`1.10`, then
  unsupported for a stretch, then supported again from `2.8` onward).
- **`CompatRegistry`** stores package constraints populated from the
  automatically discovered data of `feu.compat.discovered` (loaded by
  `get_default_compat_registry()`), and user calls to `register_compat()`. A
  target registered with an empty list of ranges is explicitly
  unsupported, whereas a package/target with no entry is unconfigured and
  accepts any version.

  A lookup target matches a stored entry when `python_version` and
  `free_threaded` are equal, and each of `os`/`arch` is `None` in the entry
  (wildcard), `None` in the lookup (unspecified: any platform) or equal.
  Among the matching entries, the most specific ones (most non-`None`
  `os`/`arch`) are kept and the answer is the union of their ranges.

## Discovery

`discover_compat_targets(pkg_name, targets=DEFAULT_TARGETS, *, companion=None,
ignore_versions=None)` computes compatibility data from PyPI rather than
requiring it to be hand-maintained, with one algorithm for every package. For
each release, it parses the wheel file names (via `WheelTag` /
`parse_wheel_filename`) and the `requires-python` metadata to determine, per
target (Python version, OS, arch, free-threaded), the range of package
versions that support it. It returns a `Discovery`: the considered versions
and the ranges of each target.

A package whose wheels do not carry the platform tags is described by data, not
by a class: a *companion* package (`SameVersion("jaxlib")` for `jax`,
`PinnedDependency("polars-runtime-32")` for `polars`,
`PinnedDependency("pydantic-core")` for `pydantic`, see `COMPANIONS`) and the
releases to ignore (`IGNORED_VERSIONS`, e.g. `duckdb` `0.0.0`). For such a
package a pure-Python wheel says nothing about the platform and never counts:
the release is judged by its platform wheels, or by the wheels of the
companion release. Pass `companion=` or `ignore_versions=` to handle a new
case.

The discovered data powers the built-in compatibility data under
`feu.compat.discovered`: these modules are regenerated by
`dev/generate_discovered_compat.py`, run on a schedule by the
`bot-update-discovered-compat` CI workflow
(`.github/workflows/bot-update-discovered-compat.yaml`).

## Usage

```pycon
>>> from feu.compat import Target, find_closest_version, is_valid_version
>>> target = Target(python_version="3.11")
>>> is_valid_version("numpy", "1.23.2", target)
True
>>> find_closest_version("numpy", "0.1.0", target)
'...'

```

Corrections can be registered on top of the built-in discovered data:

```pycon
>>> from feu.compat import Target, register_compat
>>> from feu.compat.registry import VersionRange
>>> register_compat({"mypkg": {Target(python_version="3.12"): [VersionRange("2.0", None)]}})

```
